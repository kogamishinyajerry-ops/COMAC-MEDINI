# COMAC-MEDINI 双线验收报告：代码、干净检出与安全边界

日期：2026-09-22。基线：`0ac71ebc17b1c4db161b49956853e57733b68692`。

本报告是一次代码与自动化测试验收，不是 Medini 实机验收、独立专业安全审查或适航用途批准。PR 保持 Draft，未合并 master。未接触真实型号数据、未执行真实 Medini 写作业。

## 1. 决策结论

继续双线建设，但当前不应标记为“工程交付完成”。A 线已经具备可测试的执行/治理代码；B 线有可独立复核的计算与存储基础。下一轮优先完成可复现交付、安全边界和真实工作流证据，不优先堆叠新界面或扩大方法覆盖。

分开设置四道门：

1. **可检出/可运行**：另一台干净机器从指定提交启动，依赖与源码完整。
2. **确定性方法**：限定语义与资源范围，独立实现和负例验证。
3. **授权业务闭环**：真实工具、真实权限、版本绑定、可恢复执行和完整证据。
4. **获准用途**：业务负责人基于预先约定用途和证据批准。前三道门不自动等于第四道。

当前 B 线第 1 道门失败；A 线非实机测试仍有失败。部分数学校核通过，不能据此越过后续门。

## 3. 问题清单与处置

### R1 / P0：B 证据源码未进入可交付提交

位置：`native-safety-analysis/src/native_safety/cli/main.py` 对 `native_safety.evidence.bundle` 的导入；对应测试收集日志。

影响：CLI、报告/证据及部分 FMEA 路径无法在干净检出运行。根目录与 B `.gitignore` 的未锚定 `evidence/` 规则会同时忽略同名源码包。

本 PR：收窄忽略规则，保护源码路径。**修改 ignore 不会恢复文件**；应由原开发者从工作区/备份恢复真实实现并提交。禁止创建空壳模块、跳过证据测试，或把旧 JSON 输出当作源码恢复。

验收：`git check-ignore -v native-safety-analysis/src/native_safety/evidence/bundle.py` 不应命中运行目录规则；源码在 `git ls-files` 中；干净导入、全套测试及 FMEA 独立验证通过。

更正：此处已验证的缺失模块是 **B 线**；不能把它泛化成 A/B 两线证据包都缺失。A 入口在上述运行中成功导入。

### R2 / P1：A 按锁龄抢占会破坏单写者保证

位置：`medini-agent-automation/src/medini_automation/application/writer_lock.py`。

基线行为：超过 `stale_after_s` 即删除旧锁并进入，即使原进程仍在写。记录抢占日志不能阻止两个作业同时修改。同进程同秒的 PID/时间组合也不是唯一持有权凭据。

本 PR 修复：
- 保留现有 `writer_lock(scope, root=..., actor=..., wait_s=..., stale_after_s=...)` 接口。
- 已存在、老旧、不可读及格式错误的锁均拒绝自动抢占；`stale_after_s` 仅作兼容元数据。
- 每次持锁增加唯一 token；释放时只匹配自己的 token。
- 等待使用单调时钟，拒绝负数和非有限等待值；写入失败保留记录而非不确定地开放写入。
- 新增进程间竞争、老锁、损坏 JSON、外来 token、异常退出、不同 scope 等回归。

兼容性注意：依赖“15分钟后自动解锁”的调用方必须修改操作规程。既有测试若断言自动抢占，应改为断言拒绝并走恢复程序；不能删除安全测试以恢复绿灯。

恢复规程：暂停所有入口，确认相关写进程和工具作业全部停止，回读工程、归档锁和作业记录，再由受控管理员解除；重新运行只在新的工作副本进行。PR 没有引入无人值守强制解锁接口。

边界：此方案针对可信本地文件系统上的合作进程；不声称覆盖网络文件系统、恶意删除锁文件或分布式 fencing。禁止在写者仍活动时人工删除/替换锁文件。

### R3 / P1：B 审批人名字不是认证凭据

位置：`native-safety-analysis/src/native_safety/store/repository.py`，`NON_APPROVING_IDENTITIES` / `_assert_approver`。

现有实现拒绝部分 Agent 名称，其余字符串作为审批人返回。这能避免部分误操作，但不能证明提供字符串的一方是获授权人类。拥有同等调用/文件权限的 Agent 可以选择一个不在黑名单的名字。

本 PR 不用更长黑名单假装修复身份问题。建议将其明确限定为可信本地操作者约定，不用于无人监管生产审批。

后续必须实现：可信服务取得的主体身份、权限检查、提案者/审批者职责分离、绑定目标基线和 patch 哈希的授权、过期与重放拒绝、Agent 不可取得的审批凭据、审计与撤销。失效、伪造、基线变化和机器主体越权必须各有反例。

A 线是否满足这一完整威胁模型也应单独验证；存在签名或审批相关代码不自动等于部署权限隔离已经成立。

### R4 / P1：A Gold 候选生成测试仍失败

上述初次运行有四项 Gold 候选/生成闭环相关失败，日志包含 `KeyError: 'gold-01-simple-or'`。应针对同一提交重现，检查候选索引、加载器和输入契约之间的映射，再缩成最小回归。尚未完成根因修复，不将其归咎于未经确认的“缺少某个目录”。

不能通过删除失败用例、改成 skip，或临时制造“已批准 Gold Case”来解决。业务 Gold Case 需要专家批准与来源；数学示例和候选材料不是业务验收真值。

### R5 / P2：B 异常输入尚有非结构化异常路径

位置：`native-safety-analysis/src/native_safety/domain/validation.py`。

静态阅读确认：入口使用 `data.get` 前未验证根对象；遍历事件/门时直接对元素调用 `.get`；0.1.0 事件缺少 probability 时可走 `raw['probability']`；非字符串 gate kind 可进入集合成员判断。应补 `ModelError` 回归，避免 AttributeError/KeyError/TypeError 泄露为接口500。

本次只登记问题，未修改该大模块。已有 `basic_events_independent is True` 的严格校验应保留；不要误报为接受字符串 'false'。同样不要改动精确概率或失效率语义来应付输入测试。

验收输入：非对象根、数组里的 null/数字、缺少概率、kind 为数组/对象、condition 非字符串；同时既有合法例题结果逐位不变。

## 5. 双项目共用的验收台账

每个能力一行：`capability_id / scope / assumptions / input_schema / kernel_or_adapter_version / supported_limit / baseline_sha / evidence_level / last_verified_at / result / blocker / owner`。

建议证据等级：`SOURCE_REVIEW`、`UNIT_TESTED`、`INDEPENDENTLY_CHECKED`、`MOCK_WORKFLOW`、`REAL_TOOL_VERIFIED`、`BUSINESS_ACCEPTED`。允许同一能力有多种证据，禁止从“有代码/有脚本”直接升级到“真实工具已验证”。

首批业务小树包括：简单 AND/OR、重复事件、k/n 的限定语义、稀有事件、非法结构拒绝、失效率任务时间条件、FMEA-FTA追溯断链、版本变更后结果失效、作业中断恢复，以及独立封存的同类新任务。种子数字不等于专家认可的真实工程失效率。
